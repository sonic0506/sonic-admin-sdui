# 인터랙션 테스트 세부 기준

여기 적힌 것은 **원칙**이다. 함수 이름, import 경로, 테스트 작성 위치(`play` / `.test()` 등)는 Storybook MCP 지침과 설치된 버전을 따른다.

## 1. 요소 찾기

우선순위 (위에서부터 시도):

1. **role + 접근 가능한 이름** — 버튼, 링크, 입력, 체크박스, 다이얼로그 등
2. **label** — 폼 필드
3. **placeholder** — label이 없을 때만 (label이 없다는 것 자체를 보고에 언급)
4. **text** — 버튼·링크가 아닌 일반 텍스트 콘텐츠
5. **test id** — 위 방법이 모두 불가능할 때만

- role로 찾을 수 없다면 테스트를 우회하기 전에 **컴포넌트의 접근성 문제**인지 먼저 의심한다 (`div` 버튼, 이름 없는 아이콘 버튼 등).
- 같은 role이 여러 개면 이름으로 구분한다. 인덱스(`[0]`, `nth`)로 고르지 않는다.
- 존재하지 않음을 검증할 때는 "없으면 에러를 던지지 않는" 쿼리를 쓴다 (`queryBy…` 계열).

## 2. 사용자 동작

- 저수준 이벤트 발생(`fireEvent` 계열)이 아니라 **실제 사용자 동작을 흉내 내는 API**(`userEvent` 계열)를 쓴다. 클릭 전 포커스, 키 입력 순서 등이 실제와 같아진다.
- 모든 동작은 `await` 한다.
- 텍스트 입력 후 결과를 확인할 때, 입력 필드의 값보다 **그로 인해 화면에 나타난 결과**를 우선 검증한다.

## 3. 비동기

- 비동기로 나타나는 요소는 **나타날 때까지 기다리는 쿼리**(`findBy…` 계열)로 찾는다.
- 상태가 바뀌기를 기다려야 하면 **재시도형 검증**(`waitFor` 계열)을 쓴다. 단, `waitFor` 안에서는 검증만 하고 사용자 동작(클릭 등)은 넣지 않는다.
- 고정 시간 대기 금지. 디바운스·타이머가 핵심 동작이면 프로젝트가 쓰는 fake timer 방식이나 MCP 지침의 방법을 따른다.
- 로딩 상태 스토리는 응답을 **끝나지 않게** 모킹해서 로딩 UI가 고정되도록 만든다 (지연 시간을 길게 주는 방식보다 안정적).

## 4. 검증 대상

**검증한다**
- 화면에 보이는 텍스트, 요소의 존재/부재
- 사용자가 인지하는 상태: 비활성, 선택됨, 펼쳐짐, 체크됨 (가능하면 ARIA 상태로)
- 포커스 위치
- props로 받은 콜백의 호출 여부, 횟수, 인자

**검증하지 않는다**
- 컴포넌트 내부 state, ref, 훅의 반환값
- CSS 클래스명, 인라인 스타일 값 (시각 확인은 시각 회귀 테스트의 몫)
- 내부 함수 호출 순서, 렌더링 횟수
- 스냅샷 전체 비교

검증 없는 동작 나열은 테스트가 아니다. 각 인터랙션 테스트는 최소 1개의 의미 있는 `expect`로 끝난다.

## 5. 모킹

### 콜백
Storybook의 spy 함수로 args에 넣고, 테스트에서는 args를 통해 접근한다. 직접 만든 spy를 모듈 레벨에서 여러 스토리가 공유하지 않는다.

### 데이터·네트워크: 우선순위

실제 네트워크 호출은 어떤 경우에도 금지다. 아래 순서로 **가장 위에서 가능한 방법**을 쓴다. MSW 유무와 관계없이 진행할 수 있다.

1. **props 주입** — 컴포넌트가 데이터를 props로 받으면 args로 고정 데이터를 넣는다. 모킹이 필요 없다. 가장 단순하고 안정적이다.
2. **프로젝트에 MSW가 있음** — 스토리 단위로 핸들러를 지정한다. 기존 핸들러·픽스처를 우선 재사용한다. (MSW가 설치만 되고 Storybook 연동이 안 되어 있으면, 연동 설정은 설정 파일 변경이므로 승인을 받는다.)
3. **데이터 캐시 라이브러리 사용** (React Query, SWR, Apollo 등) — decorator에서 해당 라이브러리의 클라이언트/캐시에 데이터를 미리 채워 넣는다. 테스트마다 새 클라이언트를 만들어 스토리 간 캐시가 섞이지 않게 하고, 재시도는 끈다.
4. **모듈 모킹** — 컴포넌트가 import하는 API 모듈이나 데이터 패칭 훅을 Storybook의 모듈 모킹 기능으로 교체한다. 방법은 MCP 지침(또는 설치된 버전 문서)을 따른다.
5. **위 방법이 모두 어려움** — 억지로 우회하지 말고 멈춰서 보고한다. 제안할 수 있는 것:
   - 데이터를 받아 그리는 표현 컴포넌트와 데이터를 가져오는 컨테이너로 분리 (분리 후 표현 컴포넌트는 1번으로 테스트)
   - MSW 도입 (설치는 승인 후에만)

어떤 방법을 썼든 보고에 적는다. 3·4번을 여러 컴포넌트에서 반복하게 되면 MSW 도입을 환경 개선 제안으로 보고한다.

### 상태별 모킹 요령
- **Loading**: 응답이 끝나지 않도록(영원히 대기) 모킹한다. 긴 지연 시간을 주는 방식보다 안정적이다.
- **Error**: 실패 응답(HTTP 에러 또는 reject)을 반환한다. 재시도 로직이 있으면 꺼서 에러 UI가 바로 나오게 한다.
- **Empty**: 빈 배열·빈 객체 등 "데이터 없음"을 나타내는 실제 응답 형태를 쓴다.

### 그 밖의 의존성
- **라우터, 날짜, 외부 SDK** 등 네트워크가 아닌 의존성은 decorator로 감싸거나(라우터·Provider) 모듈 모킹을 쓴다. 프로젝트에 기존 방식이 있으면 따른다.
- **브라우저 API** (`localStorage`, `matchMedia`, 클립보드 등)를 건드렸다면 스토리 종료 후 원래대로 돌려놓는다.

## 6. 결정성

- 현재 시각에 의존하는 컴포넌트는 날짜를 고정한다 (props 주입 > 모듈 모킹 > fake timer 순으로 선호).
- 랜덤 ID, faker 데이터는 고정된 픽스처나 고정 seed로 바꾼다.
- 애니메이션이 검증을 방해하면 애니메이션 완료를 기다리는 검증을 쓰거나, 프로젝트에 있는 "애니메이션 끄기" 설정을 사용한다. 고정 대기로 해결하지 않는다.
- 같은 스토리를 여러 번 실행해도 결과가 같아야 한다.

## 7. Portal

Dialog, Popover, Dropdown, Toast 등은 보통 캔버스 바깥(`document.body`)에 렌더링된다.

- 캔버스 범위로 찾아서 안 보이면, 범위를 문서 전체로 넓혀 찾는다 (MCP 지침이 제공하는 방식 사용).
- 열기 동작 → 오버레이 요소를 role로 찾기(`dialog`, `menu`, `listbox`, `tooltip`, `alert`/`status`) → 내부 내용 검증 순서로 작성한다.
- 닫힘 검증은 해당 role 요소가 **사라졌는지**(부재 확인)로 한다.

## 8. 접근성

- 접근성 애드온이 있으면 모든 스토리가 위반 없이 통과하는 것을 목표로 한다.
- 위반을 없애려고 스토리에서 규칙을 끄지 않는다. 컴포넌트 수정이 필요하면 보고한다.
- 의도적으로 규칙을 끈 경우(외부 라이브러리 문제 등)는 해당 스토리에만 범위를 한정하고, 이유를 주석과 보고에 남긴다.
- 키보드만으로 조작 가능한지는 인터랙션 테스트로 별도 확인한다 (자동 검사로는 잡히지 않음).

## 9. 실패했을 때

허용되는 해결:
- 잘못된 쿼리, 누락된 `await`, 잘못된 모킹 수정
- 비동기 대기 방식을 적절한 쿼리로 변경

허용되지 않는 해결:
- assertion 삭제 또는 약화 (`toBeInTheDocument` → 아무것도 안 함)
- 스토리나 테스트를 skip 처리
- 고정 시간 대기 추가
- 접근성 규칙 비활성화
- 컴포넌트 동작을 테스트에 맞춰 몰래 변경
